# GitHub issue and pull-request lineage diagram

Apply only on an explicit request. The picture shows how issues and pull requests relate: what spawned, closed or replaced what. Read the facts from `gh`, not from memory.

`example/sample-lineage.svg` is a finished example with invented numbers, titles and people. It uses every box state, the pills, the `new` mark, the bold claim lines, a dotted frame, the legend, the find box and two collapsed boxes (#101 and #110: hover over them). It also carries every kind of fact the file keeps about itself (see "What the file keeps about itself"): a GitHub record on each box (with close reasons and a `replacedBy`), the kind and ends on each arrow, and one example entry in each list of the metadata block (`svgmeta.py show example/sample-lineage.svg`). Open it to see the look. It is built by this skill's own builder from `example/sample-graph.json`, which is also the model for the input of `build.py` (see "First revision and the scripts"). After you change a style rule here, regenerate it with `python3 example/make_sample.py` and run `check_diag.py` on it (0 failures).

## Scope

A diagram never covers the whole repository. Fix the span before you draw, write it in the diagram's notes (section "Scope"; see "What the file keeps about itself"), and ask the user, with the GitHub link, when something is unclear.

- **Roots.** The issues the user names. If the user allows it ("you may find better roots"), look for items with more related or child issues, and say which you picked and why, with links.
- **Relations to follow** from a box, in order of trust: GitHub sub-issues (`parent`, `subIssues`), closing references (`closingIssuesReferences`, `closedByPullRequestsReferences`), `blockedBy` and `blocking`, then relations the text states (`Related:`, `Blocks`, `Follow-up`, a "Children" list). A passing mention is listed but not followed; a pull request that cross-references an item is a candidate, an issue that does is only listed.
- **Filters** come from the user's prompt: state (for example open items, and closed ones closed within N days), area or label, date. Do not invent a filter; if none was given, ask.
- **The date window applies only to an item that is not in the chart yet and is not a direct child of a box already there.** An item already in the chart stays, whatever its age. A direct child (a GitHub sub-issue, a closing reference, an item the text presents as the box's child) may stay even outside the window; if unsure whether to keep it, ask. Write each such exception in the diagram's notes.
- **Ask once, not per item.** When many older direct children qualify (when the whole chart is older than the window, they all do), list them in the notes as a table (number, closing date, why kept) and put one question to the user: keep all, keep only the children of open items, or drop what is older than a date.
- **An issue reached only by a cross reference or a mention is not drawn.** List it under "Not drawn" with its link.
- **Relevance and age decide what is followed, not a hop count.** Follow without a depth limit, even outside the window: sub-issues all the way down, closing references (`closed by`), and the `follow-up` relation (the strongest after a child). `led to` is a little weaker and still important. A `blocked by` is followed while the blocker is open or inside the window. `related`, `depends on` and `references` are followed only for items that are open or inside the date window (about 30 days: a guide, not a hard rule). A mention is listed, not followed. `crawl.py` follows the structure GitHub stores (sub-issues, closing references, blockers); `follow-up` and `led to` live in the text, so read the kept items' text for them and add those items yourself.
- **Size.** Stop at the cap the user gave (default about 40 boxes) and ask what to cut: keep the roots, the open items, the closer relations and the most recent ones. There is no hop limit; `crawl.py --depth N` is only an optional safety cap.
- **Not drawn.** Every item you looked at and left out goes in the metadata block's `ignored` list with the reason (`svgmeta.py ignore IN.svg N "reason"`), so `--discover` does not report it again.
- **`crawl.py` does the walk** in one GraphQL call per level: `python3 crawl.py OWNER/REPO --seed N[,N] [--window-days 30] [--max-nodes 40] [--known N,N] [--no-up] [--out candidates.json]` (`--out` writes the kept and dropped candidates and their relations, not the input of `build.py`; see "First revision" for how to get that) (`--no-up` stops it following parents, so an umbrella's siblings do not flood the chart). It prints each candidate with how it was reached, its state and closing date, and flags `ASK` where an item outside the window was kept as a direct child. A pull request that only cross-references an item is a candidate too: it counts as a direct child only if it really closes that item (this finds pull requests closed unmerged, which `closedByPullRequestsReferences` omits). Mentions in a body are printed apart and never followed; `--text` prints the lines of each kept body that name another kept item, which is how to find `follow-up`, `led to` and `supersedes` in prose. The judgement stays with you: it cannot see that a comment calls two items the same cause, so read the titles and the dropped list.

`refresh_meta.py` takes its box numbers from an SVG's `<g id="nN">` groups, so for a first picture give it any SVG that holds the chosen numbers (an earlier diagram, or a list written with those groups).

**`graph.json`** (the input of `build.py`; `example/sample-graph.json` is a complete one): `repo`, `title`, `date`, optional `roots` (the root issues: the first column, each forks into its children; without it, the unframed source with the most forward arrows), and two lists. `nodes`: `num`, `state` (`open`, `closed`, `handclosed` for an issue closed by hand, `merged`, `waiting`, `draft`, `prclosed` for a pull request closed unmerged), `title`, `meta` (the opened/closed line), `notes` (lines), `mono` (the merge line), `assignees` (issue) or `author` (pull request), and optional `umbrella`, `new`, `frame` (the dotted frame the box belongs to), `collapsed` (keywords, only on request). `edges`: `from`, `to`, `kind` (the vocabulary below; read it as A, kind, B). A box has no x or y: the layout decides. Build it from what `gh` says, not from memory; keep `graph.json` next to the SVG if you like, but from the second revision on the SVG is the source of truth.

**Hyperlinks and references need no pattern matching from you.** Write `#N` (any number of digits) for an issue and `PR #N` for a pull request in a title, a note or the page title; `draw.py` turns each into an underlined link to the right page, with the item's title as tooltip, and `**text**` into bold. Which relation holds between two items you decide from GitHub's fields (sub-issues, closing references, blocked-by) or from what the text says, with its meaning: "blocked by", "closes", "follow-up", "supersedes". You write that as an edge, in whatever number format the repository uses.

**What the scripts do** (so you can judge a picture, not redraw it): `layout.py` reads the graph left to right. A box's column is the longest chain of forward arrows that reaches it; the rows in a column follow the average height of the neighbours (fewest crossings), a parent sits level with the middle of its children and a single child level with its parent; gaps between columns grow with the lanes they hold. A box with only weak arrows (`blocked by`, `related`, ...) gets its column from the chain of those arrows; when three or more such boxes point at one box (a hub: nine items blocked by one decision), they all go in the column right before it, as a fan. A column that holds only leaves (one arrow each, not an issue with its pull request, no arrow to another frame) is folded: each leaf sits right under the box it is tied to, with a short vertical arrow. Groups of boxes that no arrow joins inside a frame are packed against each other, so no group floats away with an empty gap. When the graph has dotted frames, each frame is a block: its boxes are laid out inside it (boxes with no arrow inside the frame are spread over a few columns, not stacked in one), the root sits in the first column level with the middle of its children and forks into them (one exit per child, nested lanes, see "Fork from a root"), the frames that hold the root's children are stacked in the next column in the order of those children, and the other frames are placed one by one, the most tied per box first (a small frame that hangs off one spot goes before a big flexible one, which then fills the space around it), where their arrows to what is placed cost least, plus the pixels the spot adds to the width or height of what is placed (`GROW_PULL`: compactness). Each arrow costs its length times its importance pull (see "Arrow vocabulary"), so a frame sits next to the frame it came from, not halfway to one it only mentions; a lineage arrow that would point right to left costs extra, so the chart reads left to right, earlier to later, without forcing it. The candidate places are below, right of, above or left of a placed frame, or level with (or straight above or below) the partner of one of their boxes, so a one-box frame lands right over its partner. Then every frame rises into free space above it, unless rising makes its arrows longer. This is tried for many column heights, and the smallest canvas between 0.9 and 2 wide to 1 tall is kept. Arrows from one column to the next get exits and entries on their sides and lanes in the gap, ordered to cross as little as possible. `route.py` routes every other arrow (it skips a column, points back, or has a box in its way) on a 5px grid through the picture as it is now: not under a box or a label, not parallel to another arrow or a frame border within 36px and 30px, crossing only at right angles, entering and leaving straight. One search covers all four sides of both boxes (the sides that face each other are preferred; another side wins when it saves a bend or a crossing), first in a window around the two boxes, then over the whole canvas before it reports NO PATH. `hops.py` draws the jump arcs. Whatever cannot be routed or labelled is printed as `PROBLEM`; say so to the user, leave that arrow out of the picture and name it in the box note.

**Comparing two layouts** of the same graph: `metrics.py A.svg B.svg` prints, for each file, canvas size and area, arrows, straight arrows, bends, total arrow length and the length of the tier-3 arrows, jump arcs, frame area and box fill. Use it with `check_diag.py` (faults) and the `PROBLEM` lines of `build.py` (NO PATH). On trial: `LAYOUT_Y=simplex build.py ...` places the rows inside each frame by network simplex (`netsimplex.py`, Gansner et al. 1993, the method of Graphviz `dot`): it minimises the importance-weighted vertical distance of every arrow's two ends, keeping each column's order and gaps, so gaps that no arrow needs close by themselves. The default stays the barycenter sweep with its gap passes. Trial result on a 152-box graph: more straight arrows (61 to 80) and fewer bends, but longer arrows in total, a different set of arrows without a path, and frame placement that reacts strongly to the new frame shapes; a reader judged the two charts about equal and kept the sweep. Try simplex again after frame placement is replaced by a standard method.


## What a node is

One box is one issue or one pull request.

Each box shows:

- the tag `ISSUE`, `PR`, or, for an umbrella, the umbrella emoji (U+2602 U+FE0F) before `ISSUE` (`☂️ ISSUE`), and the number, as a link (see Links). An umbrella is still an issue: the emoji replaces the old word `UMBRELLA`, which was too wide beside a login and a `closed` pill.
- the title
- opened date, and closed or merged date when it has one
- the merge commit, short, on a pull request
- on a merged pull request, in parentheses right after the merge commit, the usernames of its commit authors in first-commit order: `merge 3229bfa45 (alice, bob)`. With more than two, write the first and `et al.`: `(alice et al.)`. Read them with `gh api repos/OWNER/REPO/pulls/N/commits` (`.author.login`). The account that opened the pull request is a different fact; do not substitute it. A commit with no GitHub login (a null user) is named by its git author name; that is the main author. When the account that opened the pull request is different, name it after the main author: `(Yuna Seol, yunaseoul)`. With several commit authors, the main one is the author of most commits (ties: the first commit). This pair is long: put it on its own mono line so it does not run into the red cross. If the parentheses do not fit on the 11px mono line, put the authors on a second mono line. A pull request that is not merged has no merge commit, so it shows no merge line and no authors; the `by <opener>` label after `PR #N` still says who opened it.
- on an issue or umbrella that has an assignee, right after the tag and number (`ISSUE #120`): an arrow and the assignee's username, `ISSUE #120 → alice`. Read it with `gh api repos/OWNER/REPO/issues/N` (`.assignees[].login`). With several assignees, write the first username and `+N`. An unassigned issue shows the arrow and a `?`: `ISSUE #121 → ?`. A pull request shows `by` and the username of the account that opened it (`gh api repos/OWNER/REPO/pulls/N`, `.user.login`), with no arrow: `PR #122 by alice`. This is the submitter, which can differ from the commit authors.
- **The first line is ONE `<text class="kind">`** (code: `box_header.py`, the one place that draws it; `draw.py` calls it). The parts flow left to right with plain spaces and have no x or y of their own, so a longer tag or name pushes the rest: `<text class="kind" x y style="fill:STROKE">ISSUE <a>#120</a> <tspan style="font-size:15px;letter-spacing:0">→</tspan> <tspan style="font-size:11.5px;font-weight:600;letter-spacing:0">alice</tspan></text>`. Sizes: the tag is the 13.5px `.kind` class; the umbrella emoji is its own tspan at 16.9px (25% over the tag); the arrow is the character `→` (U+2192) at 15px, not a drawn polyline; the login or `by login` is 11.5px, weight 600, never smaller. The tspans set `letter-spacing:0`, otherwise they inherit the 0.3px of `.kind`. The line must end before the status pill (6px clear) and before the red cross on a closed pull request (12px clear). When it does not, the arrow and the name go on a second `<text class="kind">` 13px lower, same x. Never truncate a name. `check_diag.py` measures the line (estimated glyph widths; the width of the arrow and the emoji depends on the reader's font, so the check keeps a margin) and fails a line that ends too late. Do not move the name by hand to fix a collision and do not widen the box: use the second line.
- a design document or memo when one is the source of that item

A status pill sits in the upper right. The word is `open`, `closed`, `merged`, `waiting`, or `draft`.

| State | Box | Pill fill | Pill text |
|---|---|---|---|
| Open issue or open umbrella | `#f8e8e4` / stroke `#8a3030` | `#9f2d2d` | the box fill `#f8e8e4` |
| Closed issue or closed umbrella | gray `#eceae6` / stroke `#6e6a64` | `#4e4b48` | the box fill `#eceae6` |
| Merged pull request | `#e7f0fb` / stroke `#1d4e89` | `#163e73` | the box fill `#e7f0fb` |
| Pull request ready, waiting for review | soft yellow `#ffeb85` / stroke `#8f6400` | `#9a6700` | the box fill `#ffeb85` |
| Draft pull request (open, `isDraft`) | paler yellow `#fff6c9` / stroke `#8f6400`, **dashed** (`stroke-dasharray="6 4"`) | `#9a6700`, word `draft` | the box fill `#fff6c9` |
| Pull request closed without merging | gray, as a closed issue (`#eceae6` / `#6e6a64`), label `PR`, plus wide soft red stripes under the text (see below) | `#4e4b48`, word `closed`, with a red cross just left of it | the box fill `#eceae6` |

A draft pull request (GitHub `isDraft`, open) is drawn like a waiting one with three differences: pill word `draft` (55.0px wide), paler fill (`#fff6c9`), dashed border. All else is the same: the `PR #N by user` label, the amber pill and text, the `closed by` arrow from the issue it will close, and the note `Fix in PR #N (open).` on that issue. When the author marks it ready it becomes `waiting`: solid border, `#ffeb85`. A draft closed without merging is a closed pull request: no dash, stripes and cross. A draft is never `merged`. `refresh_meta.py` reads `isDraft` and reports the state `draft`, so a pill that still says `waiting` (or `draft` after it was marked ready) is listed as a mismatch.

A pull request closed without merging (superseded by another one) keeps its box. Its note says `Not merged: superseded by PR #N.` The arrow from the issue it meant to close becomes `work done by` (the issue was closed by the other pull request). Its follow-ups get `follow-up` arrows from it.

Marks for a closed, unmerged pull request (chosen from an experiment, option C): (1) stripes: a 22px pattern rotated 45°, a red `#b84a4a` band 9px wide at 10% opacity, drawn as a box-sized rect with the box's `rx` right after the box rect and under the text; if a later script rewrites `x`/`y` attributes, write the pattern's inner `rect` without them; (2) a red cross, two 12px lines in `#ff2a2a` (the `new` pill's red), width 2.8, round caps, centred 13px left of the `closed` pill; (3) when another pull request replaced it, a `supersedes` arrow from the replacing pull request to it. A closed issue gets the same red cross by its pill (no stripes) only when it was closed by hand, the work not done: wrong, a duplicate, won't do, won't fix, superseded, not needed. An issue whose work was done gets no cross, even when no pull request on the diagram closed it. `rules.close_verdict` decides, in a fixed order (see "Decisions made by rule"): the user's recorded answer, GitHub's close reason (`NOT_PLANNED`, `DUPLICATE`), the closer of GitHub's close event (a merged pull request or a commit: done), the phrases of its last comments, else an ASK; `refresh_meta.py --apply` adds or removes the cross from it. Its note says how it was closed (`Closed as not planned.`, `Duplicate of #N.`). When the text names what replaced it, the review asks for the arrow: `supersedes` from the replacing pull request (red-cross head), `duplicate of` from a duplicate issue to the one that remains. Closed by hand with nothing that replaced it: the cross alone. Check that the cross does not touch the `ISSUE #n → user` text. To look at one region, cut a copy of the SVG with a smaller `viewBox` (and no `<script>`) and rasterize it with `rsvg-convert`; the preview pane shows local SVG files only as static snapshots.

Open issues and open umbrellas are the same color. Closed is gray, not green.

**What an `UMBRELLA` is.** An umbrella is an issue that groups other issues: it has many child issues, and it is a tracker, not work to do directly. An issue is drawn as an umbrella (the umbrella emoji before `ISSUE`, a thick 2.6px border and a thin inner frame 4px inside it) when either of these holds:

1. It has child issues through GitHub's native **sub-issue** relation (`subIssues`, `subIssuesSummary.total` above 0 in the GraphQL query). This is the strong signal.
2. Its title says "umbrella" (for example `[Umbrella] …`). This covers umbrellas that have no sub-issues yet or that list their children in the body only.

Either is enough. A pull request is never an umbrella. A label such as `epic`, an issue form or an issue type is a project convention: it does not make an umbrella unless the user says so in the diagram's notes. `refresh_meta.py` lists every box whose label disagrees with this rule.

**An umbrella by title only has no GitHub children, so infer them.** When an issue is an umbrella only by its title (rule 2, no sub-issues), do not leave it childless and do not guess from the title; read its text:

1. Run `refresh_meta.py ... --umbrellas`. One extra GraphQL call, for those umbrellas' bodies only (never all boxes); it prints, for each, the issues named in a task list, the other issues mentioned, and which are boxes. Run it when the umbrella is new or its `updatedAt` changed, not on every revision. Never paste the body into the conversation.
2. Decide from the sentences, not from the position of the number. A **child** is an issue the body presents as work or a part of this umbrella: a "Children", "Tasks", "Scope" or "Work items" list, "this umbrella covers", "split into". A task list can also hold things that are not children: a blocker, a prerequisite, background, an earlier decision, a sibling umbrella. Words such as "blocked by", "after", "depends on", "see", "context" mark those, and they get `blocked by`, `depends on` or `related` arrows, not `child`.
3. Draw a `child` arrow for each issue you judge a child, and write in the umbrella's box `Lists #A and #B as children (read from the body).` so the reader knows GitHub does not hold the relation.
4. If it is not clear whether an issue is a child, do not draw the arrow. Ask the user, with the GitHub link of the umbrella and of the issue, and write the answer in the diagram's notes so the question is not asked again.
5. Thematic similarity alone (same area, similar title) is not enough to make a child.
6. When the umbrella later gets real sub-issues on GitHub, those replace the inferred list.

Set the pill text with a `style="fill:…"` attribute. A shared SVG text class will otherwise paint it black.

### The `new` pill

A `new` pill tells the reader what to look at first. It marks the boxes added since the previous **revision** (see "Revisions"), not since the previous edit. Mark only boxes added, never boxes whose state changed.

- An update inside the current revision keeps every `new` pill and adds one to each box it adds, however many: the revision is not over, so no pill is removed.
- When the user asks for a new revision, remove all the old `new` pills first, then put a pill on exactly the boxes that are not in the previous revision's file. Compare against that file (the frozen previous revision), not against your memory of what was added.
- When the user says to keep the pills ("build v19.1 and keep the new pills"), run `new_revision.py old new --keep-new`: the pills of the old file stay and `add_nodes.py` adds one to every box it adds. Run `check_diag.py new old --keep-new`.

- Position: on the top-left corner of the box, centered on the corner (nudge it about 2px inside), rotated −45° so it reads up and to the right across the corner. It is a corner ribbon, not a label inside the box.
- Color: bright red `#ff2a2a`, white text, a thin stroke in the page color (`draw.PAGE`) so it separates from the box edge.
- Size: the text is 1.5 times the status-pill text: 15.75px bold, letter-spacing 0.9px, set with an inline `style` (the shared `pill` class is 10.5px). The word `new` has only x-height letters, so centre the glyphs, not the text box: the baseline sits 4.2px below the pill centre, the text x is 0.45px right of the centre (letter-spacing adds a trailing gap), and there is 6.4px of space round the glyphs on every side. The pill is 47.0px wide and 21.7px tall, with fully rounded ends. Center it 3px inside the box corner, and keep a 26px half-width square around that center free of arrows and labels. (The first size, 10.5px, looked smaller than the status pills once it was rotated.)
- The `waiting` yellow is kept soft, with a dark amber border, pill and `PR #…` text, so the text contrasts with the yellow background. The `draft` yellow is paler still and keeps the same dark amber for border, pill and text.
- Keep arrows and labels clear of it. Treat it as an obstacle when you route.

### Collapsed nodes

A collapsed node is a box drawn in short form: only its first line and one line of keywords. The rest of the box shows in a pop-up when the reader hovers over it. Collapsing makes whole sections of long-closed items small, and the picture compact.

**When.** Only when the user asks for it: by box ("collapse #101 and #110"), by area ("everything in the frame X"), or by a rule they state ("the closed items in this frame"). Never by default, and never just because an item is closed or old. When the scope is unclear, list the candidates with their links and ask. Write what is collapsed, and why, in the diagram's notes (a table: number, keywords), so the next revision can collapse the same boxes again.

**What a collapsed box shows.**

- Line 1 as in a full box (one kind text, see `box_header.py`): tag (`ISSUE`, `☂️ ISSUE`, `PR`), the number as a link, the assignee or the `by` name (second line when it does not fit, as for a full box), the status pill, and the `new` pill if the box has one. The colours are those of its state.
- Line 2: the keywords, one line, class `ttl`, at most 232px wide (the same inner width as a full box). Use a few words that name the topic, not a cut-off title and not the number. Make two boxes that sit side by side (an issue and its pull request) differ in their first words: the issue says the problem (`Problem: partial reversal frees whole hold`), the pull request the fix (`Fix: partial reversal marked CMF 402`). Never truncate a title to make it fit; write new words.
- A small grey `&#8230;` at the bottom right says that there is more on hover. A `<title>` child with the full title gives a native tooltip where there is no hover.
- Nothing below the separator line: no dates, merge line or notes. They are in the pop-up.
- Height: at least 62px. It grows when many arrows end on one side (14px apart, 12px of margin top and bottom: five arrows need 80px) or when a straight arrow must keep its height (the box grows to the arrow's height plus 8px). An umbrella keeps its double border (the inner frame shrinks with the box).

**The pop-up** is a full copy of the box (same markup, links included), `<g id="popN" class="pop">`, with the same top-left corner as the compact box, so it grows down from it. It is hidden by CSS (`visibility:hidden; opacity:0; pointer-events:none`, so Tab cannot reach its links) and shown by `#nN:hover ~ #popN, #popN:hover {visibility:visible; opacity:1; pointer-events:auto}`. It has a drop shadow. The pop-up covers the boxes under it while it is open; that is accepted. Never give the pop-up a transition that keeps it open after the pointer left.

**State lives in the SVG.** The first `<rect>` of a collapsed box has `data-collapsed="1" data-keywords="the keywords"`. A comment in the SVG says so. The visible text is made by `collapse.py`, so after an edit of the keywords, run the script again; do not edit the text lines by hand.

**Tools.**

- `python3 collapse.py in.svg out.svg --set 101="keywords" --set 110="keywords"` (or `--spec collapse.tsv`, one `N<TAB>keywords` per line). It collapses in place: each box keeps its top-left corner, the arrows that end on it are re-attached to the new edges with their shape and lanes kept (arrows between boxes that did not change stay as they are), the labels move to a straight stretch, the CSS and the pop-ups are written. `--set` on a box that is already collapsed only changes its keywords. `--expand N,N|all` puts the full boxes back from the pop-ups (arrows are not touched; run check_diag.py). `--no-cue` leaves out the `&#8230;`. `--remove N,N` deletes boxes from the diagram (only when the user says so; it refuses while an arrow still ends on the box). `--center` makes a straight arrow between two collapsed boxes with the same top run through their centres (without it the arrow keeps its old height, which can leave it near the bottom of a short box).
- `--shrink-frames` pulls the bottom edge of each dotted frame up to its lowest box (plus the old bottom padding). Nothing else moves.
- `--moves moves.json`: `{"boxes": {"123": 3251}, "frames": {"frame title": {"y": 100, "h": 420}}}` gives the new top y of boxes and the new y and height of frames; the script moves them, re-attaches the arrows and updates the canvas. You do not compute that file: `compact.py` does (next bullet).
- `python3 compact.py in.svg out.svg` closes the empty space that collapsing or removing boxes leaves. It reads the diagram as it is: boxes of one frame and one column keep their order and move up to 28px apart when the gap between them is over 60px (a tighter gap may carry arrows and stays; 100px where a vertical arrow with a label joins two of them; a gap where a bent arrow ends on the bottom of the upper box or the top of the lower one stays, since that arrow runs in it), boxes joined by a straight horizontal arrow move together so it stays straight, a frame shrinks to its lowest box and what lies below it in the same columns moves up by the same amount; then it calls `collapse.py` for the moves (arrows re-attached, labels moved to a straight stretch), routes again with `route.py` every arrow the move left invalid, and redoes the jump arcs. It never moves a box sideways or down, and it refuses to write the file when the move would leave more invalid arrows than before (it names them): collapse fewer boxes at a time, or use `--force` and fix them. When the user asks to compact one area, pass `--frame WORDS`: only that frame (and the frames inside it) closes its gaps; what lies below it in the same columns moves up by what it saved, and no other gap changes. Then `reroute.py OUT OUT --in-frame WORDS --improve` gives its inner arrows the shorter routes that opened up. `collapse.py` re-slots only the arrows of the boxes it collapses in that run: a box collapsed by an earlier run keeps its height and its arrow ends (later steps may have set them), and an arrow with jump arcs whose two ends move apart is rebuilt as a plain polyline (the arcs are drawn again at the end). Run `check_diag.py` afterwards.
- The hover mechanism does not change between revisions; only an edit of the file can break it, and every such break is in the text: a box without its pop-up or rule, a rule or pop-up without its box, a pop-up away from its box's corner, a missing hiding rule, a pop-up after the `<script>` or not a sibling of its box, or something drawn after the first pop-up (SVG has no z-index: a later element paints over the open pop-up). `check_diag.py` checks all of these on every run, in well under a second. That is the hover check of a revision.
- `node test_hover.mjs diagram.svg 101 110 [--shot out.png]` hovers over each box in a headless Chromium (0.7s per box) and says whether its pop-up became visible and is the topmost element at the pointer. Run it ONLY when the user says hover is broken somewhere, and only on the boxes named, to find what the static check misses (for example a CSS syntax error that stops the whole style sheet). Never as a routine step.
- A collapsed box is just a smaller rectangle with a pop-up; the pop-up floats over the picture and takes no part in any layout computation. Do not keep a second, full version of a diagram: start each revision from the previous collapsed file (`new_revision.py`, which also drops the pills in the pop-ups), refresh it with `refresh_meta.py --apply`, add the new boxes and arrows with `add_nodes.py`, and collapse or compact only when asked. `svg_state.apply()` runs in two passes: the boxes as drawn (a collapsed one gets only what its small form shows: colour, state word, assignee label) and then the pop-ups, which get every edit (state, date line, merge line, "Closed by" note) and need no room check. `add_nodes.py IN.svg OUT.svg spec.json [--snapshot snap.json]` adds new boxes and arrows (the spec format is in its docstring): it finds free space beside the box a new one relates to (`near`), inside the frame it belongs to (`frame`, which grows when needed); a box with arrows to two or more boxes takes, of the nearest free spots above and below in every column beside `near` and in its frame, the one with the least total distance to all of them (`_place_best`). When no free spot is near, open room by hand (`band.py` under the frame's title) and give the box `"x"`, `"y"` in the spec; it routes each arrow with `route.py` in the diagram as it is, places the labels, moves the legend when a new column goes right of it, grows the canvas, and redoes the jump arcs. It prints every new box as `x y w h` and a `PROBLEM` line for what it could not do. It moves no other box. The order of a revision: `new_revision.py` → (once, for a file drawn the old way) `box_header.py restyle NEW NEW` → `refresh_meta.py --apply` → `add_nodes.py` → `check_diag.py NEW OLD`. Read the whole list of edits that `refresh_meta.py --apply` prints (and its `NEEDS A HUMAN` lines), never only the last line. The records the next refresh compares `updatedAt` against are in the boxes (`data-github`): there is no snapshot file to keep.

**Layout after collapsing.** Collapsing in place leaves empty space. Close it, in this order, and then run `check_diag.py`:

1. Inside a frame, stack the collapsed boxes with a pitch of box height plus about 14px (a vertical arrow between two boxes needs 80px for its label). Put a parent or a closing pull request at the middle of its children, so the middle arrow is straight and the fork spreads up and down, with the lanes nested (the higher an up-arrow starts, the nearer its lane; the lower a down-arrow starts, the nearer its lane).
2. Shrink the frame to its content: 40px above, 20px below.
3. Move the frames below it up by the same amount, and everything that hangs on them (boxes, frame titles, arrows). A column of frames keeps 34px of visible gap. Where a frame is next to other frames (not only above and below), a frame that moves up must not run into the frame on its side: the checker fails overlapping frames.
4. Look at the changed regions once (render only that region, not the whole canvas). A second pair of eyes helps here: a reviewer who knows these rules finds overlaps and dead gaps a script does not measure.

**Pitfalls.**

- The find box script (`find-box.js`) moves every node that exists when it runs into an inner `<svg>`. The pop-ups must come BEFORE the `<script>` element, and boxes and pop-ups must be direct children of the root, so that the sibling selector `#nN:hover ~ #popN` still matches at run time. This shipped broken once: pop-ups written after the script stayed outside the drawing and never showed. `collapse.py` writes them before the script and `check_diag.py` fails the other order.
- When the user reports broken hover, test it in a real browser engine (`test_hover.mjs`), not with a render: `rsvg-convert` and the built-in browser pane (no viewport, static snapshots) cannot hover. GitHub, Quick Look, `<img>` and a PDF show no pop-up either; there the reader gets the keywords and, where the viewer supports it, the `<title>` tooltip. Say so when the picture will be shared that way.
- The find box also matches the text of a pop-up (`find-box.js` adds it to the box's text), so a search finds a collapsed box by a word of its notes.
- Do not wrap boxes or frames in a `<g>`: it breaks the sibling selector and the checker's box pattern.
- A state change is applied to the small box and to its pop-up by `svg_state.py`; a note that says "(open)" and must be edited by hand is reported for the pop-up as well.
- A `closed` pill (62.4px) is wider than an `open` one (47.6px); when a collapsed box's state changes, run the name check again.
- Many arrows on one small box are hard to read. The 14px spacing is the least; if a box would need more than about six per side, leave that box expanded.

## Links

Every issue number and every pull-request number is a link to the GitHub page. Issue `#N` goes to `https://github.com/OWNER/REPO/issues/N`. Pull request `#M` goes to `https://github.com/OWNER/REPO/pull/M`. Use the repository that owns the item. In SVG, wrap the number text in `<a href="…">` and underline it (`<tspan style="text-decoration:underline">#N</tspan>` inside the link).

- Underline EVERY issue or pull-request number that is a link, not only the one in the box heading: the mentions in a title, a note (`Blocks #125`), the legend, the page header and a frame title too. A clickable number with no underline looks like plain text.
- Put a `<title>` child inside each `<a>` with the item's title (browsers show it as a tooltip on hover): the box's title for a box, otherwise the title read with `gh`; leave it out if unknown. Escape the text.

If the user asks for a PDF, those same numbers are links there too. A PNG cannot hold a link. Do not promise links on a raster.

## What an arrow is

The picture is a directed graph, not a tree and not an acyclic graph. Most arrows point forward in time, from the earlier item to the later one (`child`, `follow-up`, `led to`, `spawned`, `revised by`, `closed by`, `work done by`). A few point back or sideways by design: `blocked by` runs from the blocked item to the blocker, `supersedes` from the newer pull request to the older one, and `related`, `depends on`, `references` and `mentioned` have no direction in time. So a cycle can appear (an item that blocks another item it also led to). That is fine: do not drop a true relation to avoid a loop, and do not call the picture acyclic in the title, description or legend.

- A source is an item no forward arrow (`child`, `follow-up`, `led to`, `spawned`, `revised by`, `closed by`, `work done by`) points into. The root issue (or umbrella) the diagram starts from is that kind of node. When the user starts from several initial issues, each is a source.
- Read every arrow as a sentence from tail to head: A, label, B. `#10 closed by #12`. When the later item acts on the earlier one, the label is passive (`closed by`, `revised by`, `work done by`). A noun label (`child`, `follow-up`) names what B is to A.
- Use only the labels in the vocabulary below. If none fits, add one to the table first, with its definition; never invent a label in the picture or use two labels for one meaning. The same table is `EDGE` in `draw.py`: a new word goes into both.
- When a pull request closed an issue, say the pull request number on the issue box as well.
- If two items both come from the same item, draw two arrows out of that item. Do not draw an arrow between the two siblings. Parallel is not a chain.
- A node may have no outgoing arrow. An open issue with no pull request is that kind of node. It still has its incoming arrow.
- A relation named in a box's text has an arrow, if both items are boxes. This holds for `Related: #N`, `Blocks #N`, `Blocked by #N` and a decision on one item that another item must wait for (issue A is blocked by the decision recorded on issue B). On every revision, compare the boxes named in each new or updated item's text with the arrows, with a small script: list each pair where one text names the other and no arrow joins them, then read only the "Related", "Blocks", "Closes", "Follow-up" and "Found" lines. A passing mention does not need an arrow (`mentioned`). If the route would cross the whole picture, say so to the user instead of dropping it silently.
- An open pull request that closes an issue gets the same blue `closed by` arrow as a merged one (state is in the pill, not in the arrow). Each issue it closes ends its note with `Fix in PR #N (open).`; when the pull request merges, that line becomes `Closed by PR #N.` A pull request's box repeats only its own facts (`Closes #A and #B.`, tests, evidence); it does not name other boxes unless an arrow joins them. Relations that appear only in the pull request's description, far from it in the picture, are left out unless the user asks.
- Two open pull requests that close the same issue each get a `closed by` arrow from that issue, and each says "PR #N also closes it."
- An umbrella may list a child that is older than the umbrella (umbrella `#40` lists `#25`, which `spawned` it). Do not draw a `child` arrow: it would run against the `spawned` arrow and make a loop of forward arrows, which reads as a mistake. Write the child in the umbrella's box (`Lists #25 and #31 as children.`) and use the bold `Blocks` / `Blocked by` lines.

### Arrow vocabulary

| Label | Line | `A → B` means |
|---|---|---|
| `child` | solid, ink | B is a formal child of umbrella A: B is a GitHub sub-issue of A (`parent`), or, where sub-issues are not used, A lists B or B names A as its parent. |
| `follow-up` | solid, brown | B was filed to finish something that A left out. |
| `led to` | solid, brown | Work on A produced B, including a defect that work on A exposed. (There is no separate `found` arrow. The box text says "Found ...".) |
| `spawned` | solid, brown | A caused B to be filed as a new umbrella or work stream. |
| `revised by` | solid, brown | B is a later pull request that changes what pull request A delivered. |
| `closed by` | solid, blue | B is the pull request that closed issue A. |
| `work done by` | dashed, blue | B did work for A but did not close it. A was closed by hand, or stays open. This includes a pull request that tried to close A and was closed unmerged, whether or not another pull request replaced it. |
| `evidence, does not close` | dashed, amber | B gives evidence for A. A stays open. |
| `supersedes` | solid, red `#b02a2a`; the head is a red cross `#ff2a2a` (about 16px, its centre exactly on the box border; the marker needs `overflow="visible"`; the arrows come before the boxes in the file, so `xmarks.py` draws the cross again in a layer after the boxes: it lies on top of the closed box's border and is whole) instead of an arrowhead | A is the pull request that replaced B. B was closed unmerged. The arrow runs from A to B. Put the label on a long vertical stretch, not on a short horizontal one: a red-cross head leaves little shaft. Draw it when GitHub or the text says, in any wording, that one replaced the other: "supersedes", but also "we prefer X, so Y is closed", or Y's approach is wrong, obsolete or stale and X takes over. Judge by meaning, not by keywords. Two pull requests for the same issue, with nothing like that said, are not enough: keep `work done by` and `closed by`, and ask. |
| `duplicate of` | solid, red `#b02a2a`, an ordinary (red) arrowhead on B, and a red cross at its start, on A's border, on top of A (`xmarks.py`) | Issue A was closed as a duplicate of B; B remains and carries the work. The arrow runs from the closed duplicate to the issue that remains. A gets the red cross (closed by hand), by its pill and where the arrow leaves it. GitHub's "marked as duplicate" event, or "duplicate of #B" in A's text, says so; `rules.py review` asks for the arrow when it is missing (`duplicate-missing`). |
| `blocked by` | solid, dark red `#8a3030` | A cannot be finished until B is done: A's text, or B's, says B blocks A. The arrow runs from the blocked item to the blocker. |
| `depends on` | dashed, gray | A needs the result of B, but B does not block A's work. Use `blocked by` when the text says "blocked by" or "blocks". |
| `references` | dashed, gray | A's text points to B as relevant prior work. |
| `mentioned` | dashed, gray | A names B in passing. B is not part of this lineage. |
| `related` | dashed, gray | A and B are related work. Neither is the parent of the other. |

**Importance.** Each word has a weight for the reader (`draw.IMPORTANCE`): very important `child`, `closed by`, `blocked by`, `depends on`; medium `follow-up`, `led to`, `spawned`, `revised by`, `work done by`, `evidence, does not close`, `supersedes`, `references`; low `related`, `mentioned`. The layout uses it twice. A frame is placed where its important arrows are short (an arrow pulls its two frames together at 1, 0.6 or 0.2 of its length), and the router draws the important arrows first, so they get the short, simple paths and a low one is what is left without a path when space runs out. With `graph_from_snapshot.py --low-as-notes`, a low arrow between two different frames is not drawn at all: it becomes a note on its tail box (`Related: #N.`), since such a line crosses the chart for little meaning. A new word goes into `draw.EDGE` and `draw.IMPORTANCE` together.

### Bold claims in the box text

A claim that is true now, and that a reader must not miss, is bold. Write it with `**...**` in the note text.

- `Found ...` (where the defect came from) and `Blocks #N.` are bold while the box is **open**.
- **`Blocked by`: one line per blocker.** `Blocked by #2 and #3 (Q2): why` is drawn as `Blocked by #2` and, on its own line, `Blocked by #3 (Q2): why` (the qualifier and the explanation stay on the last blocker's line, as in the sentence). Each line is **bold** while the box and that blocker are both open (only the clause, never the explanation), and ~~struck through~~ in normal weight once either is closed: the block is over. A block is also over while both are open when GitHub no longer links that blocker to the box and the picture states no such block either (no `blocked by` arrow between them, none in `nopath`): the link was removed, so the line's claim is stale (`svg_state.blocker_holds`; `check_diag.py` uses the same function). A block known only from a text keeps its arrow, so it keeps its claim. A text sentence that a removed link outdates (the body still says `Depends on #3`) is a decision: take its arrow out with `svgmeta.py drop`, which records it in `nopath` so the next refresh does not draw it again. A closed box is blocked by nothing, so all its lines are struck. A blocker that is not a box and whose state is unknown keeps its claim (bold). One rule does this everywhere, `rules.blocked_notes`: `graph_from_snapshot.py` applies it to the lines in `notes.json` (and adds one line for a `blocked by` arrow that no note names), and `refresh_meta.py --apply` (`svg_state.reblock`) applies it to **every** box and pop-up at each refresh, since a blocker that closes changes the boxes it blocked and GitHub does not mark them as updated. A box that needs another line grows; with no room below it, `svg_state.make_room` inserts a band of free space under it (`band.py`) when a line that cuts no box exists inside its frame, else it is reported: move a box (`move.py`) and refresh again. Marked words wrap like any other (`draw.wrap_px` measures bold ones in the bold face); the note markup is `**bold**` and `~~struck~~`.
- `Not merged: superseded by PR #N.` (or another reason for a closed, unmerged pull request) is bold: it is the one fact that tells a reader the box delivered nothing, and it stays bold because the box will never change state again. Read the reason from GitHub, not from guesswork: who closed it (`closed by the author`, `closed by a maintainer`, or `closed as maintainer-only` when it carries such a label; `crawl.py` prints it) and, for a closed issue, its state reason (`Closed as completed.`, `Closed as not planned.`); write `closed without merging` when it is unknown.
- `Decision needed: ...` (a question a human must answer before the work can go on) is bold on every line while the issue is **open**. When it closes, the line is not bold and reads `Decision was needed: ...` (or the decision itself, if known).
- When the box is closed or merged, the `Blocks` line goes away (it blocks nothing now; the `blocked by` arrow stays as history). `Found ...` stays, but not bold.
- An open umbrella is `Blocked by` its open children, and each open child says `Blocks #umbrella.` This holds only while the umbrella is open: if it was closed (or any blocked item was closed, merged or abandoned), write neither line, because closing it shows it was not blocked; the open child is then just an open child. Write this only when the item is a formal child of the umbrella, or the umbrella's text lists it. The reverse is not implied: if umbrella `#40` lists `#25` in its task list, `#25` blocks `#40`; a sibling umbrella that does not list `#25` gets no line.
- An item can block several umbrellas: `#31` says `Blocks #1 and #40.` One relation is written once on each box (`Blocks #U` on the child, `Blocked by #C` on the umbrella). It is not a mutual block.
- When an umbrella's body lists children, its box says so (`Lists #25 and #31 as children.`) and names the decisions that have no issue yet. Do not leave `No child issue yet.` after the body has changed. Re-read the umbrella body on every revision.
- Do not bold `Closes ...` or `Closed by ...`. They are frequent and the `closed by` arrow already shows them.
- When a box grows (note lines added), check its bottom edge is still inside its dotted frame; if not, grow the frame and move the frames below it.
- When you add a line to a box, grow only the two box rectangles (width 260 and 252). Never grow a rectangle by its `rx` alone: the status pill has `rx="10"` too, and it doubled in height once.

A dotted frame may name an area (a module, a component, a theme). The frame does not replace an arrow. Do not put the parentage only in a section title.

## Layout

`build.py` and `add_nodes.py` apply the rules of this section by themselves (`layout.py`, `route.py`). Read them to judge a picture and to explain a choice, not to redraw it by hand.

Use the plane. Rows and columns are for alignment, not a substitute for edges.

- Leave a gap long enough that the opaque label does not cover the whole shaft: tail and arrowhead stay visible. A gap under about 150px is too small for a `closed by` label.
- Draw every path first, then every label, so a later path cannot hide an earlier label. Labels sit on top of the stroke.
- Put the label on a long segment of its arrow, not on a stub or on a bus shared by many arrows (a shared bus stacks the words).
- A label always stays on its own arrow. When an arrow moves or is routed again, its label moves with it (to another stretch of the same arrow if needed); a jump arc splits a stretch like a bend. `collapse.py`, `compact.py`, `add_nodes.py` and `build.py` do this, for a label of any height (a two-line one too). A label found with no arrow under it was left behind by an older edit: `model.py relabel` puts it back on the nearest arrow of its word that has no label.
- When one item has several children, fan the arrows. A vertical column of children with the parent on one side and the closing pull request on the other is the pattern: arrows leave the parent and enter each child; `closed by` arrows leave those children and converge on the pull request. Give each arrow its own vertical position so labels do not overlap and every arrowhead shows.
- **Fork from a root (required).** Put the root level with the middle of its children, so its arrows spread up, straight ahead and down, not all downwards. Give the root's right edge one exit per child, 14 to 16px apart, and make the root box taller if it needs the room. The arrows share one vertical bus between the root and its children, nested so none crosses; never send all the arrows downwards, and do not leave from the bottom edge in a staircase. Lane order, so nothing crosses: for arrows going up, the topmost exit takes the lane nearest the root; for arrows going down, the lowest exit takes the nearest lane (the exit farthest from the middle is the nearest lane). Size the gap between the root and its children at 14px per lane plus about 60px at each end (never under 205px). The root box must be tall enough that every exit leaves from its right edge: an exit below the box is a defect, and the checker flags a tail that does not touch a box. Keep each exit-to-child jog at 30px or more, or make it straight: when neighbouring exits are packed and cannot move, move the arrow's entry point along the child's left edge (anywhere at least 20px from the corners) instead. The lane count for the gap formula is the larger of the up group and the down group.
- **Several roots.** Each root has its own cluster (its children and its frames); do not run a root's arrows across another cluster, and repeat a shared theme as a frame in each cluster. There are two layouts, and the user may choose: (a) every cluster starts in the first column, stacked, so the x axis is one timeline from root to outcome; (b) the second cluster sits to the right of the first, which keeps the canvas near square. Default (hybrid): stack (a) while the canvas stays shorter than about 1.3 times its width, and start the next cluster to the right when it would not; side by side also when the user asks. If the finished canvas is at least twice as tall as wide (or twice as wide as tall), stop and ask the user before going on; `check_diag.py` prints a note then. The legend does not move: it stays in the top row, with its right edge at the right edge of the rightmost box or frame of the whole drawing (the farthest right node edge fixes it; or further right, in a column of its own). Never leave it left of that edge. A cluster placed to the right of the first starts below the legend, not beside it.
- Do not route an arrow through a box. If a box sits between two ends, go around it in a gutter.
- A closed side branch (an item and its pull request, often in their own frame) is a candidate for removal. The more of these signals hold, the stronger the candidate:
  - It is a side topic, not part of the lineage.
  - Everything in it is closed or merged.
  - All the work was done by someone else (the authors and assignees are not the person who asked for the diagram).
  - Nothing open waits on it.
  - Only a weak arrow reaches it (`depends on`, `related`, `references`, `mentioned`).
  - It closed before the lineage's own work started.
  - It sits alone in its own frame.

  When you remove one, keep one line in the box that used it (`Used #30 (closed by PR #31).`). A branch with only one or two signals stays. If you are unsure, ask with the GitHub link.
- The "How to read this graph" legend is compact and always sits in the top row, with its right edge at the farthest right edge of the nodes (the top-right of the chart; see "Several roots" for a second cluster). When columns are added on the right, move the legend with them. It has no "Still open on <date>" summary. It explains the pills, the arrow words and the bold lines.
- Frames stacked in one column share a left edge, with about 34px between them. A frame must never overlap a frame of another column: compare all frame extents after every change. When a frame grows or is inserted, the frames below it move down by the same amount with their boxes, arrows and labels. Order stacked frames so the arrows from the source nest without crossing (see the lane rule below).
- Trunk arrows that run down a gutter beside a column of frames each get their own lane, about 14px apart, in the same order as their start points on the source (so they do not cross), and enter their box from the left. Put their labels on the last straight stretch.
- The canvas ends about 80px below the lowest box or frame. Compute it from the final geometry, not from numbers the build used before frames moved.
- Anything that is specific to one diagram (the order of its frames, its column widths, a frame that must stay, a lane assignment) goes in the diagram's notes, inside the SVG (`svgmeta.py notes IN.svg` prints them, `--from FILE` replaces them; `example/NOTES_template.md` is the outline). Read them at the start of every revision and update them in the same revision. No file lives next to the diagram. This skill holds only rules that hold for any repository.
- **Every revision starts with `refresh_meta.py` (in this skill's directory), and re-checks every box, not only the ones the user mentioned.** `python3 refresh_meta.py OWNER/REPO diagram.svg --apply` makes ONE GraphQL call for all boxes (box numbers come from the `<g id="nN">` groups). GitHub's `updatedAt` changes on any edit, comment, label, assignee or state change, so the script compares it with the record each box keeps (`data-github`) and prints only the boxes that changed, with the differing fields (state, title, assignees, comment and review counts, merge commit and its commit authors, opener). It also prints every box whose pill disagrees with the live state. Read the full text of a box only when it is listed as changed. It writes the new records back into the boxes on every run. Run it outside a sandbox that blocks TLS. Fix every difference in the same revision, and say in the answer how many boxes were checked and which changed. The cost of a no-change revision is this one call.
- **Dates are the reader's dates.** GitHub gives UTC timestamps; `refresh_meta.local_day` turns each into a date in this machine's time zone (or `TZ`), so an item merged in the evening west of Greenwich is not shown on the next day. `--apply` rewrites both dates of every date line (`opened D` and `closed D` or `merged D`) at each refresh, in boxes and pop-ups.
- **The first line is laid out again at each refresh.** `box_header.refit` runs on every box: when the login (a new assignee, a longer one) or a wider pill no longer lets the line end before the pill, the arrow and the name go to a second line 13px lower, as the builder draws it (a full box has room above the title). A collapsed box is only reported: run `collapse.py --set N=...` again, which places the keywords under two lines. A header on two lines that would fit on one is left as it is.
- **Label marks are per chart.** A chart whose metadata block has `"label_marks": [{"label": "<GitHub label>", "letter": "x", "fill": "#rrggbb"}]` gets a 19.5px round pill with that white letter before the tag of every issue that carries the label (before the umbrella emoji too; the first listed label wins). The pill holds `<title>label: NAME</title>`: a tooltip, and box text the find box matches. With `"border": true` an open issue with the label gets its border in that colour; any other state keeps the state colour. `refresh_meta.py --apply` reads the issue labels and adds or removes the mark (`box_header.set_mark`); a chart without the key gets no marks. Set the key with `svgmeta.read`/`svgmeta.write`.
- **State changes are applied by script, not by hand.** Add `--apply` to the same call: `svg_state.py` edits the SVG in place for the changes that are pure text edits on a box: pill word, width and colour, box fill, stroke and dash, the `opened ... still open | closed D | merged D` line, the assignee label, a missing `merge <sha> (<authors>)` line on a merged pull request, and a `Closed by PR #N.` note on an issue closed by a pull request that is a box. Each of the last two makes the box 14px taller and is applied only when the box has room below it and inside its frame. A changed title is applied too (`svg_state.retitle`): the title lines of a full box and of a pop-up are wrapped again as the builder wraps them, the lines below them move by the change in height, and a box that needs another line grows only where it has room (else it is reported); a box whose title needs fewer lines keeps its height (arrows touch its bottom edge and the sides below it; a short gap under the title is harmless); the tooltip of every link to that item, anywhere in the picture, gets the new title (`retitle_links`). A collapsed box shows its keywords, not its title: it keeps them. When a box grew, `--apply` places the labels again (`model.relabel`), since the arrows into its bottom got shorter. **A box whose `updatedAt` changed is brought up to date in full, not only its state:** besides the edits above, `--apply` reads its body and last comments in the same extra GitHub call and looks at its relations to other boxes (`relate.py`): a new GitHub link (sub-issue, parent, blocked by, blocking, closed by) or a relation its text states by the phrase rules of `rules.py` (`Blocked by #N`, `Closes #N`, `Follow-up to #N`, ...; a negated phrase does not count) becomes an arrow, routed in the picture as it is (through `add_nodes.py`), one per pair (the strongest word, `rules.RANK`); a weak word (`related`, `references`, `mentioned`) is only reported, as is a pair drawn with another word or listed in `nopath`. A GitHub link the box had at the last refresh and no longer has (unblocked, a sub-issue moved, a closing link removed) takes its arrow out, unless the text still states it. Each drawn or removed arrow is printed with its reason (the link, or the sentence). `relate.py IN.svg [N ...]` prints, from the records the file keeps, which GitHub links are not drawn (no network). Everything else is printed as `NEEDS A HUMAN` (a closed unmerged pull request, an ISSUE that should be an UMBRELLA, a note that still says `(open)` or `(draft)`, a merge line or a title without room): do those by hand (a text edit of the box). An existing merge line is never rewritten. A title shortened by hand is rewritten to GitHub's: keep a short form only by asking the user to retitle the item on GitHub. After `--apply`, run `check_diag.py`; the edit does not move any box or arrow.
- **A new revision starts with `new_revision.py old.svg new.svg`:** it copies the file (never overwriting) and drops every `new` pill; then run `refresh_meta.py ... --apply` on the new file.
- **Use GitHub's own relations, not only the text.** GitHub stores real relations between issues and pull requests. Ask for them in the same single GraphQL query as the metadata (`refresh_meta.py` does, and `--relations` lists every one that joins two boxes):
  - Parent and child: `Issue.parent{number}`, `Issue.subIssues(first:50){nodes{number}}` and `subIssuesSummary{total completed}`. A sub-issue is a **real** `child` of its parent. Draw a `child` arrow for it, and treat the old rule (the body lists it, or it names the parent) as the fallback for repositories that do not use sub-issues. Compare `subIssuesSummary.total` with the children you drew: a difference is a child that is not a box.
  - Closing: `PullRequest.closingIssuesReferences{nodes{number}}` (what a pull request closes) and `Issue.closedByPullRequestsReferences{nodes{number}}`. These are the `closed by` arrows, and they are more reliable than a `Closes #N` line in a body, which can be wrong or edited. A pull request can close several issues, and an issue can be closed by several pull requests.
  - Blocking: `Issue.blockedBy(first:20){nodes{number}}` and `Issue.blocking(first:20){nodes{number}}` (GitHub's issue dependencies) give the `blocked by` arrows. When they are empty, the box text is the only source.
  - Where a relation exists on GitHub but not in the diagram, draw it. Where the diagram shows a relation GitHub does not have (a `Related:` line, a decision), keep it: the text is evidence, not an error.
- **Minimize GitHub API calls.** One aliased GraphQL query for all boxes (about 3 s for 91 boxes, about 4 points of the hourly budget; add `rateLimit{cost remaining}` for the real cost). Detect change with `updatedAt` against the box's record and read a box's text only when it changed. The relations above ride in that same query, so they cost no extra call. When a box changed and you need its new comments, ask for `comments(last:N)` with `N` from the comment count difference, never for all of them. Do not call `gh issue view` or `gh pr view` per box, do not fetch bodies you do not need, and never print a body into the conversation. Everything the diagram shows (title, state, assignees, opener, merge commit, authors, relations) is in the one query. Not measured: whether a relation change alone moves `updatedAt`; `refresh_meta.py` therefore stores the relations in the record and prints any difference.
- **Speed and token tips (measured on 87 boxes: 48 s with one `gh api` call per box, 3 s with one GraphQL call):**
  - One query with aliases, `i123: issueOrPullRequest(number:123){...}`, asking only for the fields the diagram shows (title, state, `updatedAt`, assignees, opener, comment count, merge commit). 87 boxes cost 3 of 5000 rate-limit points. Above about 200 boxes, split into several queries.
  - Never reread the text of a box whose `updatedAt` did not change.
  - Find new items with `gh api 'repos/OWNER/REPO/issues?state=all&since=T&per_page=100' --paginate --jq '<only the fields needed>'`, filter in the script, and print only the items that link to a box. Never print issue bodies into the conversation.
  - Do the sync in one command and the edits and the check in a second one. A revision should need about five tool calls: refresh and discover, read only the changed or new items, add boxes and check, render one crop, update notes.
  - `gh` sandbox and token rules: see Requirements.
  - Most of the elapsed time is the model's reasoning, not the scripts (measured: about 85% model, 12% tools). So let `add_nodes.py` decide placement from the geometry of the file and the diagram's notes, and keep a new box in free space rather than shifting neighbours.
- **Finding new items:** add `--discover`. It lists the issues and pull requests created, closed or merged since the last run (the metadata block's `lastRun`; `--since ISO8601` looks further back and does not move it) that are not boxes yet. It prints in full only the ones that name a box (`#N` in the title or body) or are named by a box's text. The rest is compressed: same-area items (the `area:` title prefix) as a list of numbers, and counts of unrelated, only-commented and ignored items. Items that were only commented on or edited are not candidates. Judge thematic relation from the title and the area list; open an item only when that is not enough. Every reported candidate must end the revision as a new box, or as a decision: ask the user about doubtful ones (with the GitHub link), then add the declined ones to `ignored` (`svgmeta.py ignore`) so they are not reported again.
- A candidate that only mentions a box in passing is not worth a box. Draw a new item only when it closes, blocks, follows up, supersedes or decides something about a box, or sits in the same thread of work. When in doubt, the diagram stays smaller: ask, and put every "no" in `ignored` (`svgmeta.py ignore`).
- Without `--discover` the script finds changes only in boxes that already exist.
- A revision that adds boxes the user has not confirmed is written to a separate file (the user names the version, for example `<diagram>_vX.Y.test.svg`), and the kept file stays untouched. Updating existing boxes (state, assignee, text) still goes to the kept file. When the user says to keep the same version, overwrite that file.
- When a frame moves, only the arrows that cross its border change. Redraw those through the gaps between frames, use a jump arc where they cross another arrow, and move a label that the new route would cover. Then run the check script.
- Prefer a wider picture to a crossing. When a crossing cannot be avoided, see "Hard arrows" below.

### Compactness

Make the picture as compact as clarity allows, so it fits a screen or a page better. The order of priority is: clarity first, then no unintended overlap and no crossing, then compactness.

- Use both directions. Do not let the picture grow only down a long column or only across a long row.
- Keep gaps tight. Between stacked boxes, about 25–30px. Between dotted frames, about 35px of visible space. Frame padding, about 40px above (room for the frame title) and 20px below. A horizontal gap is as wide as its longest label plus about 50px of visible shaft, and no wider.
- Boxes sit in aligned columns with the same gap (about 200px) between neighbours. Only a gap that carries a fan of many nested lanes may be wider (about 14px per lane plus margins). When you narrow a gap, keep each lane's distance to its box edge and squeeze only the middle.
- A label longer than the gap minus about 100px goes on two lines (for example `evidence,` over `does not close`, in a label about 98px wide and 30px tall). Do not widen a gap for one long label.
- Look for large blank areas and consider moving a node, or a whole framed group, into one, only if the arrows stay easy to follow: no new crossing, no arrow that doubles back across the picture, no box that hides the flow from earlier to later.
- A column that holds a single box at the end of a chain can often fold under its neighbor, with a vertical arrow. Keep the vertical gap long enough for the label and a visible tail and head (about 80px for `closed by`: an 18px label, about 25px of straight shaft above and below it, and the arrowhead). Measure the shaft as the straight line only, from the tail to the base of the arrowhead (tip minus about 11px), and center the label on it so both visible shafts are equal, even when shorter than on a horizontal arrow. An error up to about 6px is fine; centering on the tail-to-tip span, off by half the arrowhead, is acceptable.
- Good groups to move have few incoming arrows and none leaving, such as a separate umbrella linked to the source only by dashed references; moving such a frame from the bottom of a long column into a blank area can cut the height by about 20%.
- When a moved group's incoming arrows must cross a column of boxes, give them a corridor: leave a horizontal gap between two frames (about 30px per arrow), run each arrow along its own line in it, then turn toward the target in the gutter before the target's frame. Treat the corridor height as the arrow's target height when ordering trunks, so it nests with the others and nothing crosses. Put the label on the last segment, which enters the box. One corridor is fine; each additional long one makes the source's fan harder to read, so weigh it against the height it saves.
- Keep an arrow at least about 30px from a frame's dotted border when it runs parallel to it. A dashed arrow next to a dotted border reads as one line.
- When a change makes the picture smaller, compare the before and after rasters. If following an arrow is harder after the change, undo it.

### Hard arrows

Some arrows have no clean path: the tail's side is full of other arrows, or a column of boxes sits between the ends. Do not let them shape the layout. Finish the main layout with every easy arrow first, then route the hard ones, fewest options first, with `route.py`, a search on a 5px grid that reads the arrows already drawn (`build.py` and `add_nodes.py` call it), not by eye.

Rules for a hard arrow:

- Never draw it under a box or under a label. Keep it about 26px from boxes and 7px from labels, and clear of any `new` pill. A label keeps 7px from every other arrow too (`route.place_label`).
- An arrow between two boxes of the same frame stays inside that frame, with as few bends as it can (an almost hard rule: `route.py` searches the frame first, and leaves it only when no path exists inside; `check_diag.py` fails it then).
- Spacing comes from the labels. Two parallel horizontal arrows are never closer than 22px (`route.HARD_H`): their 18px labels then fit one above the other with a 4px gap, and that is also the pitch of the entries on one side of a box. Two parallel vertical arrows are never closer than 14px (`route.HARD_V`); their labels go at different heights, so a label (35–41px each side of its line) does not reach the other arrow. Closer than 42px (`route.LABEL_ROOM`) a vertical pays a small cost per step (`route.NEAR_COST`), so it leaves room for a label when that is cheap; a short tight way still beats a long detour around the picture.
- Costs of the search (`route.py`): a 5px step 1, a bend 30, a crossing 35 (barely more than a bend: a crossing with a clean jump is not much worse), a side other than the facing one 20, a border of a frame that holds neither end 60 (through it: 120), a border of a frame that holds one end or both 75 (leaving it and coming back: 150).
- A low arrow (`related`, `references`, `mentioned`) from closed work that would travel far (`rules.far_low`) is not drawn; it goes to `nopath`.
- It may cross another line only at a right angle, and only on a long straight stretch: at least about 30px from either line's bends and from its arrowhead. Never turn on top of a line.
- Draw each crossing as a small jump: a semicircle of about 7px radius, over the line already there. A horizontal arrow hops up. A vertical arrow hops to the right. The older line stays straight. `hops.py` (in this skill's folder) adds the missing arcs and removes arcs that hop over nothing; it also merges the points a removed arc leaves inside a straight run (the router keeps away from every point of a path, so such a point can close a channel). `add_nodes.py` and `collapse.py` call it by themselves; run `hops.py IN.svg OUT.svg` only on a diagram whose arrows were edited by hand.
- A crossing (with a clean jump) and a bend cost about the same (35 and 30): do not add several bends to save one crossing, nor the reverse. Do not leave a jog shorter than about 30px; a flat lane at a slightly different height is better.
- Put the label on a long straight stretch, away from every jump and from other lines.
- A SHORT arrow (no stretch can carry its label, not even with 8px of shaft each side, as between two stacked boxes) has its label BESIDE the middle of its longest stretch, 5px from the line: right of a vertical stretch, else left; above a horizontal one, else below (`route.place_label_beside`). A long arrow whose stretches are blocked never gets one: that is a routing problem, reported as before. Every script places a label in that one order, 20px of shaft, then 8px, then beside (`route.place_label_any`). A script that routes arrows places their labels before `hops.py` draws the jump arcs, so a straight arrow whose middle is crossed found no place and lost its label; `move.py` and `reroute.py` therefore end with `model.label_missing`, which labels each routed arrow that still has none in the finished picture (the arcs cut it in pieces that may carry it), and print a PROBLEM for one that still has no place.
- Each hard arrow keeps its own entry point on the target's edge, 22px or more from the others on a left or right side, and enters it straight for at least 25px before the arrowhead.
- After the rules change, or after boxes moved, run `reroute.py IN OUT --improve`: it tries every arrow again, the most costly first (`route.path_cost`), and keeps a new path only when it costs less, in two passes. It never makes an arrow worse by that measure (a jog under 30px counts as `route.JOG_COST`, since the search cannot see stretch lengths).
- A route the user chose is pinned: `data-pinned="1"` on the arrow (`svgmeta.pin`). `--improve` never touches a pinned arrow, though a cheaper route by the numbers exists: the user weighed things the costs do not see. `move.py` pins every arrow named in its `--sides` or `--reroute`; pin others with `reroute.py IN OUT --pin A>B ...` (`--unpin` undoes it). When a revision starts from an older file, pin the routes the user asked for before running `--improve`: an older file may predate the pins, and an unpinned corridor the user chose comes back as the route the costs prefer (it happened: an arrow the user had sent below a row went back over it).
- An arrow with no path costs little time: before its last, whole-canvas search, `route.py` walks back from the target over the moves the search allows (with the turn rules: most failures are "no room to bend before the box", not "walled in"), and when that walk reaches no start there is no path. Before it, the failed searches were most of the routing time (5 arrows, 69% of a full reroute).
- Where a spacing number comes from: the user's own examples of good spacing, measured in the file. The 22px pitch is two arrows into one box whose labels sit one above the other with a hair of gap; the 7px label clearance is a vertical pair whose labels sit at different heights, 10px from the other arrow, which the user said could be 20–30% less. When the user points at an arrow as good or bad, measure it (`svgmeta.py` gives its ends, the path gives the numbers) and turn it into a constant with its reason, not into a one-off move.

**A reroute-only revision (vN.1)** (the rules changed, or the user asks for cleaner arrows, and no box, state or pill changes):

1. `cp vN.svg vN.1.svg` (no `new_revision.py`: the pills of vN stay).
2. `reroute.py vN.1.svg vN.1.svg --pin A>B ...` for every route the user chose in this conversation or earlier ones (moves with `--sides`, corridors, "make it go below").
3. `reroute.py vN.1.svg vN.1.svg --improve` (about a minute for 200 arrows). Read its last lines: the total path cost before and after, and each `MORE BENDS` arrow, which traded bends for crossings, frame borders or length. Name those to the user.
4. `check_diag.py vN.1.svg vN.svg --keep-new` (the pills are kept on purpose).
5. `render_region.py` on the regions the user cares about, in both files, and one overview at reduced width.
- If no path meets the rules, leave that arrow out of the picture, name it in the box note and in your report, and say what would have to move to make room. Do not draw it with a worse path.

## Files

### Revisions

A **revision** is a named, frozen version of the diagram. It is the unit the `new` pills are measured against. The default naming is a `vNN` suffix on the file name, starting at `<diagram>_v1.svg` (later `<diagram>_v11.svg`, `<diagram>_v12.svg`); if the user names versions another way (dates, tags, `rev-3`), use theirs and keep it consistent. Ask once if it is unclear, and write the choice in the diagram's notes.

- **An update is not a revision.** A refresh, a state change, a new assignee, a new box, a new arrow, a text fix: all of these edit the current revision's file in place: same file name, `new` pills not reset (see "The `new` pill").
- **A new revision starts only when the user asks for one** ("make a new revision", "this is v13", "start v13"). Then copy the current file to the new name, leave the old file frozen (never edit it again), reset the pills as described above, and put the revision name in the title block or the diagram's notes.
- A variant of the current revision (for example a more compact layout) takes a decimal, `_v7.1`, and is a separate file.
- When the user says to keep the same version, overwrite that file.
- A new box is not a reason to start a revision. If you are unsure whether the user wants a new revision, keep editing the current one and say so in the answer.
- A diagram with collapsed boxes (see "Collapsed nodes") needs no full companion file. Name the file for what it is (`<diagram>_v15.1_collapse.svg` is a variant of v15.1, like a compact layout); do not write a `_full` file next to it.

Small corrections edit the current SVG; write a new `_v2`, `_v3`, … file only when the user asks for a new revision or the layout is being replaced.

An extract is a separate SVG of one dotted frame with its boxes, arrows and labels, cut at the frame border with a clip. It keeps the `new` pills, and it may carry the "How to read this graph" block above it (without the "Still open" lists). Build it by selecting elements from the finished diagram, not by drawing it again. `extract.py IN.svg OUT.svg --keep N,N,... [--title TEXT]` does that for any set of boxes, across frames: it keeps those boxes where they are, with the arrows between them (routes, labels, pop-ups and links as the user approved them), drops the rest, shrinks each frame that lost boxes to what it still holds (at most 60px margins, never beyond its old border), drops empty frames, moves the legend to the new right edge, drops metadata entries that name a box outside the extract, and shrinks the canvas. Without `--compact` it never routes again, so empty bands stay where dropped frames were, and an extract of boxes far apart opens on an empty corner. `--compact [ANCHOR]` is the usual choice for a handout: the anchor frame (the frame whose title starts with ANCHOR, else the one with the most boxes) moves whole to the top-left, under the header, with its boxes, arrows and labels unchanged; every other frame (a satellite) is drawn again, small: its boxes in columns by their own arrows (the longest chain, as `layout.py` does), each column ordered by the height of the anchor boxes they join, 200px between columns, 50px between boxes, at least as wide as its title. The legend goes to the top of a right column; the satellites follow below it, the most joined to the anchor first, as far down as the anchor frame reaches; the rest go in a row below the anchor. Then every arrow with an end on a satellite box is routed again (`move.move`, the most important first) and gets one `--improve` pass. The user asked for this after a faithful extract opened on empty space: the important frame must be the first thing seen.

Do not emit a PDF unless the user asks for one. When they do, keep the issue and pull-request numbers as links.

### What the file keeps about itself (`svgmeta.py`)

The SVG is the diagram's only file. Besides what it draws, it keeps the facts a later revision needs, where browsers ignore them (the picture, the find box and the pop-ups do not change):

- **On each box** `<g id="nN">`: `data-frame`, the full title of the frame it belongs to (absent: outside every frame), and `data-github`, what GitHub said at the last refresh (compact JSON: `updatedAt`, state, title, assignees, opener, counts, merge commit, dates, native relations). A box and its record cannot come apart: copy or delete the box and the record goes with it.
- **On each arrow** path: `data-from`, `data-to`, `data-kind` (read: from, kind, to). Several kinds share one arrowhead, so the kind is never guessed from the drawing.
- **One `<metadata id="diagram">` block** after `<desc>`, for what has no box or arrow of its own: `format`, `repo`, `roots`, `lastRun` (the last refresh, which `--discover` starts from), `ignored` (items looked at and left out, each with a reason), `nopath` (arrows that are true but not drawn: NO PATH, a low arrow turned into a note, or one the user dropped, each with a reason), `decisions` (dated lines: what the user decided that the drawing alone does not explain, by whom), `notes` (markdown: scope, revision naming, rules for this diagram; outline in `example/NOTES_template.md`), and `accepted` (review findings the user answered "keep", see "Decisions made by rule").

Rules:

- Only scripts write these facts: `build.py`, `add_nodes.py`, `refresh_meta.py`, `collapse.py`, and `svgmeta.py` for the rest (`decide`, `ignore`, `nopath`, `drop`, `notes`, `kind`), and `rules.py accept`. Never edit them by hand.
- When the user drops an arrow or decides something the picture cannot show, record it in the same revision: `svgmeta.py drop IN.svg A B "reason"` (removes a drawn arrow and keeps it in `nopath`), `svgmeta.py nopath IN.svg A B KIND "reason"` (one never drawn), `svgmeta.py decide IN.svg "text" --by NAME`. An arrow that `add_nodes.py` draws later leaves `nopath` by itself.
- Everything here travels with the file. Write facts and neutral reasons only, never remarks about people.
- `check_diag.py` runs `svgmeta.problems()`: it fails when a box sits outside the frame its `data-frame` names (or inside one it does not name), when an arrow has no attributes, when its drawn ends or its arrowhead or label disagree with them, when a `nopath` arrow is drawn, or when an `ignored` item is a box. A box with no `data-github` yet is a warning (the next `refresh_meta.py` stores it). A file with no block is an old file: one warning; migrate it on the next revision.
- `svgmeta.py show IN.svg` prints the block and how many boxes and arrows carry their attributes.

### Decisions made by rule (`rules.py`)

Some choices used to be judgment. Each now has a fixed rule with a fixed tie-break, so two agents (or two models) with the same inputs make the same choice. A rule proposes; the agent checks it against GitHub, and what no rule can decide is asked of the user and recorded in the file.

| Choice | Rule | Where it runs |
|---|---|---|
| the kind and direction of an arrow from text | `rules.PHRASES`: an ordered list of phrases; the first that matches a sentence of A naming B gives the kind and direction. A phrase does not count when it is negated or quoted just before it ("does not close", "Remove 'Closes #N'"), or when another item's number stands right before it ("#X closed by #B" in A's text is about X). A sentence naming three or more boxes that matches no phrase is a list and gives nothing | `mentions.py --candidates` |
| one arrow per pair | `rules.RANK`: the strongest kind wins | `mentions.py`, `graph_from_snapshot.py` |
| the frame of a new box | `rules.frame_for`: each arrow to a box already drawn votes for that box's frame with its importance (3, 2, 1); the roots do not vote; ties: a frame before none, then more arrows, then the lowest-numbered neighbour. A box whose only arrows go to a root is an ASK | `add_nodes.py`, for a box whose spec has no `frame` |
| the box a new one goes beside | `rules.near_for`: the most important arrow, then the lowest number | `add_nodes.py`, for a box whose spec has no `near` |
| why a closed issue was closed (the red cross) | `rules.close_verdict`: the user's answer (`rules.py closed IN.svg N hand\|done "reason"`), then GitHub's close reason, then the closer of the close event, then the phrases of the last comments (`HAND_TEXT`, `DONE_TEXT`), else ASK | `refresh_meta.py` stores it in the box record and `--apply` draws it; `graph_from_snapshot.py` for a new chart |
| an arrow inside one frame | `route.route`: when both boxes are in one frame the search is that frame's inside; it leaves only when no path exists there (`sc.left_frame`), and `check_diag.py` fails such an arrow (`reroute.py --frame-leavers`) | `build.py`, `add_nodes.py`, `reroute.py` |
| a far low arrow from closed work | `rules.far_low`: a `related`, `references` or `mentioned` arrow whose tail is closed or merged and whose path is longer than 8 times the median arrow, or passes through a frame that holds neither box, is not drawn; it goes to `nopath` with the reason | `build.py`; `rules.py prune IN.svg` on a diagram; `check_diag.py` warns |
| arrows to look at again | `rules.review`: `stale-far` (a medium or low arrow from work that ended a week or more before the last refresh, across two frames, longer than 8 times the median arrow) `supersedes-missing` and `duplicate-missing` (a box closed for, or as a duplicate of, another box, with no arrow between them) and `number-order` (a `led to`, `follow-up`, `spawned` or `revised by` arrow to a lower number: GitHub numbers items in creation order, so the tip came first) | `check_diag.py` prints them as `ASK` lines; they never fail |

- Put every `ASK` to the user, with the GitHub links. Record the answer: keep the arrow with `rules.py accept IN.svg A B CHECK "reason"`, or drop it with `svgmeta.py drop IN.svg A B "reason"`. Either way the next review does not ask again.
- `rules.py frame IN.svg N --arrows 'A>N:kind,...'` shows the vote for a box before adding it. `rules.py selftest` runs the phrase rules against a fixed set of sentences; run it after any change to `PHRASES`, and add a sentence for the case you fixed.
- `route.py selftest` (about 1s) routes small fixed scenes, one per routing rule: the frame border costs (read from the cost the search found, `route.LAST_COST`), the 22px horizontal spacing, no crossing near a line end, the fast no-path proof, the middle label of a straight arrow, the jog cost, pinning. Run it after any change to `route.py`, and add a scene for the rule you fixed: a rule that silently stops working (the frame border cost once did, for many revisions) shows only as slightly worse pictures, never as an error.
- Change a rule only for a reason that holds in any repository, never to fit one diagram.

### Interactive find box

Embed `find-box.js` (in this skill's folder) in the SVG, in a `<script type="text/javascript"><![CDATA[ … ]]></script>` element as the last child of the root, in the full diagram and in extracts. `build.py` does it, and `example/sample-lineage.svg` is the reference. Do not rewrite the script; it is finished and works in Chrome, Safari and Firefox. It opens the drawing at 65% of its drawn size (the user found 100% too large, its text too big; 75% was tried first); that start size is the reader's 100%. `data-scale="0.5"` on the root `<svg>` sets another start size for one file. A renderer without a window keeps the drawn size. The start size changes only the drawing (the inner `<svg>`): the find box keeps its own size (330px wide at browser zoom 100%). Chrome keeps one browser zoom for every `file://` page, so a diagram opened after another one was zoomed out opens zoomed out too, and the find box can then look small where the zoom guess fails; Cmd+0 (Ctrl+0) resets it.

What it is: a search box pinned at the bottom-left of the window, in a deep-blue panel that stands out from every box colour. Like the Shift + scroll hint it is half transparent (the panel's background at 55%, the whole box at 75%), so it does not hide the drawing under it; it turns solid while the pointer is on it or the field has the focus. It builds itself when the SVG is opened, so a renderer that ignores scripts shows the unchanged static picture, and it never changes the geometry of the drawing. How it is built, in short: at load it moves the drawing into an inner `<svg>` in a `foreignObject` that fills the window, inside a scrollable HTML container, and puts the box in an overlay outside the scrolling area, so the box stays where it is while the picture scrolls. It sizes everything in explicit pixels from the window size and redoes it on resize. It keeps about the same size on screen when the page zoom changes (the page zoom is estimated from `devicePixelRatio`, with a separate branch for Firefox and for Safari). If the window gives it no size (a thumbnail), it puts the drawing back as it was.

- A number (`120` or `#120`) jumps to that box, centred, and highlights it. If no box has that number, it matches numbers that start with what was typed.
- Any other text (`alice`, `bob merged`) matches every box whose text contains all the words, so it finds assignees, `by` submitters, commit authors and titles (for a collapsed box, also the text of its pop-up). Operators, no parentheses: `&&` is AND like a space, `||` is OR and binds looser, `!word` is NOT (`intent && !closed`, `alice || bob merged`); `#120` inside an expression is box 120 exactly. Each GitHub label in the box's `data-github` record is also searchable as `label:NAME` (never drawn; `refresh_meta.py` keeps the labels current). Hover tooltips (`<title>`) and label marks are not part of the text. The field turns pale green on a match, pale pink with a red border on none, white when empty. The `regex` box makes the query one case-insensitive JavaScript regular expression; Escape on an empty field turns it off. Matches get an orange glow, the other boxes and the arrows fade, and the current match has a magenta border. Every arrow that starts or ends on a match stays bright and thicker (with `click-highlight.js` in the file, also its halo and glowing label), and the box at its other end fades only a little (`nb`), so the reader sees where each match connects without counting it as a match. Enter and Shift+Enter, or the arrow buttons, move between matches. Escape, a double-click on the diagram outside the box, or the cross clears it (the `regex` box stays as it is). Press `/` to focus it.
- `file.svg#120` and `file.svg#find=alice` run the search on load, so a link can point at a box.
- It runs only when the SVG is opened directly in a browser, or embedded with `<object>` or `<iframe>`. It does not run in `<img>`, in GitHub's preview, in Quick Look or in a PDF. To test the matching logic without a window, call `window.lineageFind('alice')` (it returns the numbers of the matches); to test the layout, load the file in a headless Chromium (`--screenshot`, with `#120` in the URL).
- The pop-ups of collapsed boxes must come before the script element and be direct children of the root (see "Collapsed nodes", pitfalls).

### Shift + scroll zoom

`shift-zoom.js`, the third page script (`<script id="shift-zoom">`, after the click highlight; `refresh_scripts.py` puts all three in). Hold Shift and turn the mouse wheel, or scroll up or down on a trackpad: the drawing grows or shrinks around the pointer (10% to 300% of its drawn size). With Shift held, macOS sends a vertical scroll as a horizontal one, so the script takes whichever moved. A plain scroll still scrolls. It changes only the size of the drawing; it never touches the browser zoom or find-box.js's handling of it, and it gives the reader a zoom that has none of the browser zoom's glitches. A small half-transparent hint, `Shift + scroll to zoom · 100%`, in the red of the `open` pill, sits to the right of the page title as the page opens, level with it (centred on the title line's height) and 0.75 hint-widths after its end (under the header when the window is too narrow), and stays there on screen, the same size under the browser zoom, like the find box. It counts from the start size (100%); a click on it goes back to the start. `window.lineageShiftZoom` has `scale()`, `start` and `zoomTo(scale, x, y)` for a test.

### Click highlight

`click-highlight.js` (in this skill's folder) is a second script, `<script id="click-highlight">`, right after the find box script; it runs after the find box has moved the drawing into its inner `<svg>`. `build.py` and `new_revision.py` put both scripts in through `refresh_scripts.py`, so each new revision carries the skill's current scripts; run `refresh_scripts.py IN OUT` only on a file made some other way. Running it twice gives the same file.

- Click an arrow or its label: the arrow lights up in its own colour (a halo under the line, the line 3.4px instead of 1.9px, the label with a thicker border, a glow and bolder text, its red cross if it has one), and the two boxes it joins get the orange frame of a find-box match. Nothing fades.
- Click a box (or its open pop-up): the box gets the magenta frame of the current find-box match, every arrow that starts or ends on it lights up as above, the box at the other end of each gets the orange frame, and everything else fades (boxes, arrows, labels, crosses; frames and the legend stay).
- Escape, or a click on the background, clears it. A click on a link inside a box opens the link and changes nothing. It has its own classes (`c-fade`, `c-hit`, `c-cur`, `c-on`), so a search and a click highlight do not clear each other.
- The click target of an arrow is a halo path the script adds under each arrow at load: 12px wide, invisible until lit (`stroke-opacity:0`, `pointer-events:stroke`). It exists only in the browser, never in the file, so it takes no part in spacing, routing or checks. It reaches 6px each side of its line; the closest arrows are 14px apart, so two halos never overlap and a click always picks one arrow.
- The file does not say which arrow a label belongs to: the script takes the arrow of the label's colour whose straight stretch runs through the label's centre (the arrow of the label's word on a tie), else the nearest one of its colour within 40px.
- To test without a person: load the file in a headless Chromium (as `test_hover.mjs` does) and send real mouse clicks (`Input.dispatchMouseEvent`); `window.lineageHighlight` has `arrow(from, to)`, `box(n)`, `clear()` and `unlabeled()` (the arrows no label was matched to: an arrow drawn without a label shows there too).

## Check

Check from the SVG text and geometry, with a script, not by looking. A script costs seconds and no image tokens. Look at a rendered image only at the end (see "Looking at the picture").

The checks below are implemented in `check_diag.py` in this skill's folder: `python3 check_diag.py new.svg [previous.svg]` (it needs Pillow and the fonts found by `fonts.py`). It prints every failure and exits 1 on a failure.

### SVG structure the checker reads

`check_diag.py` finds things by pattern, so keep this structure (`draw.py` writes it):

- Root `<svg width height viewBox>`; plain decimal numbers in every attribute (no exponents).
- A box is `<g id="nN">` whose first child is `<rect x y width height rx="10" …>` (width 260). Inside: `<text class="kind" x y style="fill:STROKE">` with the tag (`ISSUE`, the umbrella emoji tspan and `ISSUE`, or `PR`), the link, and the arrow and name tspans (see the first-line rule above; `box_header.py` reads and writes it); the status pill as `<rect … height="20" rx="10">` plus `<text class="pill">`; then `<text class="ttl|meta|note|mono" x y>` lines with x = box x + 14 and no `style` attribute (the width check reads only those).
- An arrow is `<path d="M x,y L x,y …" fill="none" … marker-end="url(#h-…)">` with horizontal and vertical segments only. A jump is an `A7 7` arc, and a path with an arc is left out of the crossing test. Draw legend sample arrows as `<line>`, never `<path>`: a path is read as a diagram arrow whose tip must touch a box.
- A box's `<g>` may carry `data-frame` and `data-github`; an arrow path ends with `data-from`, `data-to` and `data-kind`; one `<metadata id="diagram">` follows `<desc>` (see "What the file keeps about itself"). Keep `d` the first attribute of an arrow: several scripts read it by position.
- An arrow label is `<rect … rx="4" fill="#fffdf7">` followed by `<text class="lbl">`, centred on a straight stretch of its own arrow. A label beside a short arrow keeps those x and y on the shaft (so every script finds its arrow the usual way) and carries `transform="translate(dx,dy)"` on the rect and its text lines: that is where it is drawn (`draw.label_box`), and what overlap checks use.
- A dotted frame is `<rect … rx="18" fill="#ffffff" …>`. A `new` pill is a `<g transform="rotate(-45 cx cy)">`.
- A collapsed box is the same `<g id="nN">`, its first `<rect>` shorter and with `data-collapsed="1" data-keywords="…"`, one `<text class="ttl">` of keywords, a `<title>` with the full title. Its pop-up is `<g id="popN" class="pop">` with the full box, a direct child of the root like the boxes, before the `<script>`. The checker does not count pop-ups as boxes.

### Measure text once

- Measure the width of each text style one time, with the real font, and keep the table: title, meta, mono, note, status pill, `new` pill, edge label. Use the table for every occurrence. Do not measure again for each box.
- The pill words and the edge labels are a small, fixed set (`open`, `closed`, `merged`, `waiting`, `draft`, `new`, and each label in the vocabulary). Measure each word once, then set the pill or label width from it: text width plus the padding. Do not guess a width per pill.
- Wrap titles and notes with the table, not by a character count: the inner width is 232px (box 260 minus 14px each side); bold words are measured in the bold face and wrap like the rest. Fail the check when any line is wider than the inner width of its box.

### Checks on every run (script)

- The SVG is well-formed XML. Every node has a box, a kind, a number link, a status pill and a pill word that matches the state read from `gh` (an open draft pull request is `draft`, an open ready one `waiting`).
- Content, by text search: every item in the revision appears once, as a link to the right page (`issues` or `pull`); every merged pull request shows its merge commit and its authors; every issue shows its assignee after the number, or `?` when it has none, and every pull request shows `by` and its submitter; every `closed` box has a `closed by` arrow or says why not; the source has arrows leaving it; no arrow joins two siblings; every label is in the vocabulary; pill text uses the box color; the legend and the date line name the current items and the current date.
- Geometry, from the path points and the box and label rectangles: no segment passes through a box, a label or a pill; no unintended crossing; no two parallel lines closer than the spacing rules; no label covers the tail or the head; every arrowhead enters its box straight; no jog shorter than about 30px (a warning, not a failure); every endpoint, tail and tip, touches the edge of its box; the legend is in the top row and not left of the farthest right edge of the boxes and frames (a warning); no name runs into the pill or the cross, and none is smaller than 9px.
- The first line of a box (tag, number, arrow, name: one kind text) ends before the pill (6px) and the red cross (12px); a second kind text ends inside the box.
- Frames: no two dotted frames overlap (a frame that shrinks or moves can run into its neighbour).
- Collapsed boxes: the keywords fit on one line (232px); every collapsed box has a pop-up at its corner, a `<title>`, and a hover rule; the pop-up is a sibling of its box and comes before the `<script>`; no pop-up or hover rule lacks a collapsed box; the CSS that hides the pop-ups is there; nothing is drawn after the first pop-up.
- Revision marks: exactly the boxes that are in this file and not in the previous revision's file have a `new` pill on the top-left corner, and no other box has one. Run `python3 check_diag.py current.svg previous_revision.svg`; the second file is the frozen previous revision, not a copy of the file before this edit.
- Report the largest empty rectangle. If a node or a framed group could fill it without making an arrow harder to follow, move it.
- Any arrow left out as too hard is named in the report.

When a check fails, fix the cause and run the script again. Do not look at an image to find out what is wrong.

### Faults to look for, their cause and their fix

The scripts fix the causes below by themselves. When the picture still shows one of these, find which rule did not apply (the box list and arrows of the region: read them from the SVG with `model.read`), say which script left it and why, and fix the script or the graph (a frame, a root, a missing arrow), not the SVG by hand.

| What the picture shows | Usual cause | What fixes it |
|---|---|---|
| A small group (an issue and its pull request) floats above or below its siblings, with an empty gap | the group has no arrow to the rest of its frame, so nothing pulls it in | `layout.compact_components`: the group moves up to the box above it, or, when it is already at the top, down to the group under it, never past the frame's bottom |
| An empty strip across the whole width of a frame, with a group above and a group below joined by one long arrow | the joining arrow makes the two one group, so `compact_components` leaves them; each half is centred on its own neighbours (a hub on the middle of its many tails, a small chain on its root) | `layout.close_strips`: a strip that no box of any column covers shrinks to 100px (room for one routed arrow and its label), and every box under it moves up. No straight arrow crosses such a strip, so no alignment is lost. Check every new picture for these with one look at the regions with frames and hubs (see below), and run `check_diag.py`.

### Looking at the picture

Look at most twice. Look only at crops of the regions that changed, at reduced size, not at the whole picture. `render_region.py IN.svg OUT.png X Y W H [--scale S]` (or `--box N [--margin PX]`) renders just that region: about 2s, where the whole 7000px canvas takes about 20s. To compare two revisions, render the same region of each. One overview of the whole picture at reduced width (`rsvg-convert -w 2600`) is worth it only after a change that touched arrows all over (an `--improve` pass), to see that no arrow wanders across the picture.

1. After the main layout, when boxes moved or arrows were added: one look at the changed regions.
2. At the end, after the hard arrows are routed: one look at the regions with jumps and `new` pills. Check that each hop bumps the right way and still reads as one line, and that nothing looks like clutter. Do not look at the jumps before this step.

Skip both looks when only states, dates or text changed. A PNG is only for this look. Do not keep it unless the user asks for one.
